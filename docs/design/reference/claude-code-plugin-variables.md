# Claude Code plugin variable substitution and persistent data

What Claude Code does with `${...}` tokens in a plugin's `.mcp.json` stdio
server entry, and with `userConfig` defaults and saved values, plus what
`${CLAUDE_PLUGIN_DATA}` is and how long it lives. Claude Code is closed
source; the documentation is the primary source and a probe plugin run
against Claude Code 2.1.288 on Linux settles what the documentation leaves
open. The companion page for the bundle channel is
[MCPB bundle variable substitution](mcpb-variable-substitution.md).

## Scope

- Covers: stdio MCP servers in a plugin (`command`, `args`, `env`): the
  plugin path variables, `${user_config.KEY}`, plain environment variables,
  `${VAR:-default}`, `userConfig` defaults versus saved values, and the data
  directory's lifecycle.
- Does not cover: hooks, monitors, LSP servers, remote (`http`/`sse`/`ws`)
  servers, MCPB bundles packaged inside a plugin, sensitive-value storage.
- Depended on by: `.claude-plugin/plugin/.mcp.json` and
  `.claude-plugin/plugin/.claude-plugin/plugin.json` (both generated by
  `scripts/gen_config_surface.py` from `config-presentation.domain.yml`).

Pins: no test in this repository asserts any claim below yet.

The probe: a plugin loaded with `claude --plugin-dir <dir> mcp list` whose
stdio server is a shell script that writes its environment to a file, with
`userConfig` fields whose defaults are `${CLAUDE_PLUGIN_DATA}/index`,
`${HOME}/x`, `${DOCUMENTS}/Vault`, `plain`, and one with no default. It was
run once with no saved options and once under a scratch `CLAUDE_CONFIG_DIR`
whose `settings.json` saved two of the options in `pluginConfigs`. "Probe"
below refers to these runs.

## Claims

### Plugin path variables

- `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_DATA}` and `${CLAUDE_PROJECT_DIR}`
  are substituted in a stdio server's `command`, `args` and `env`, and
  `CLAUDE_PLUGIN_ROOT` and `CLAUDE_PLUGIN_DATA` are also exported into the
  server process's environment. [source: manifest-ref] § Where each variable
  resolves [observed: probe, both `PROBE_DATA` and the exported
  `CLAUDE_PLUGIN_DATA` were set]
- `${CLAUDE_PLUGIN_DATA}` resolves to `~/.claude/plugins/data/<id>/`,
  "created on first reference and kept across plugin updates"; `<id>` is the
  plugin identifier with every character other than a letter, digit, `_` or
  `-` replaced by `-`. [source: manifest-ref] [source: components]
  [source: loading] [observed: probe, the directory existed after the run]
- The `~/.claude` part follows `CLAUDE_CONFIG_DIR`: under a scratch config
  directory the variable resolved to `<CLAUDE_CONFIG_DIR>/plugins/data/<id>`.
  [observed: probe, second run]. A plugin loaded with `--plugin-dir` gets the
  id `<name>@inline`, so its directory is `<name>-inline`. [observed: probe]
- `${CLAUDE_PLUGIN_ROOT}` "changes when the plugin updates, so don't write
  state there". [source: manifest-ref] [source: loading]
- Uninstalling from the last scope deletes the data directory, unless
  `--keep-data` is passed or another installed plugin maps to the same folder
  (or the install records cannot be read back). [source: cli-ref] § What an
  uninstall deletes and keeps
- On Windows "the substituted paths use forward slashes". [source: manifest-ref]
  [source: components]
- `${CLAUDE_PLUGIN_DATA}` was added in 2.1.78; plugin options
  (`manifest.userConfig`) became available in 2.1.83. A Claude Code that
  understands this project's `userConfig` therefore also substitutes
  `${CLAUDE_PLUGIN_DATA}`. [source: changelog] entries under `## 2.1.78` and
  `## 2.1.83`. On a version without the variable, the token would fall under
  the unset-variable rule below and reach the server literally [unverified].

### Plain environment variables

- `.mcp.json` supports `${VAR}` and `${VAR:-default}` in `command`, `args`,
  `env`, `url` and `headers`; an unset variable with no default is passed as
  the unexpanded `${VAR}` text, with a warning in `claude mcp list` and
  `/mcp`. [source: mcp-docs] § Environment variable expansion in `.mcp.json`
- Plugin servers have "access to the same environment variables as manually
  configured servers". [source: mcp-docs] § Plugin-provided MCP servers. In a
  plugin's `env`, `${HOME}` expanded to the user's home directory,
  `${HOME}/.cache/mvm` to a path under it, and `${UNSET:-fallback}` to
  `fallback`, while an unset `${UNSET}` stayed literal. [observed: probe]
- `${DOCUMENTS}` is not substituted: it is an MCPB host variable, not an
  environment variable, and reaches the server as `${DOCUMENTS}`.
  [observed: probe] (matches the comment in `config-presentation.domain.yml`)
- A default does not nest: `${UNSET:-${HOME}}/n` produced `${HOME}/n`, so a
  fallback chain such as `${HOME:-${USERPROFILE}}` cannot be written.
  [observed: probe]
- `${HOME}` resolves from Claude Code's own process environment. Windows does
  not normally define `HOME` (Claude Code's own Windows instructions use
  `$env:USERPROFILE`), so on a stock Windows install `${HOME}` would reach the
  server literally. [source: setup] for the instructions; the behaviour on
  Windows is [unverified]. What would verify: the probe plugin run on Windows
  from PowerShell.

### `userConfig` defaults and saved values

- `default` is the "Value used when the user provides nothing"; non-sensitive
  saved values live under `pluginConfigs["<plugin>@<marketplace>"].options`
  in user settings, and project or local settings entries are ignored.
  [source: manifest-ref] [source: settings-ref] § pluginConfigs
- `${user_config.KEY}` is substituted in MCP server config. [source: manifest-ref]
- A `userConfig` default is not scanned for the plugin path variables:
  `"default": "${CLAUDE_PLUGIN_DATA}/index"` reached the server as the literal
  `${CLAUDE_PLUGIN_DATA}/index`. [observed: probe]
- A default is scanned for environment variables after `user_config`
  substitution: `"default": "${HOME}/x"` reached the server as
  `/home/<user>/x`. [observed: probe] The documentation does not state this
  order. [unverified] as a stable contract.
- An option the saved `pluginConfigs` entry lacks gets the manifest's current
  default, while saved options keep their saved values, so an option added in
  a new plugin version takes its default on an install that saved the older
  options. [observed: probe, second run: saved `plain_default` and
  `home_default` came through as saved; unsaved `data_default` and
  `docs_default` came through as their defaults]
- An optional option with no default and no saved value is substituted as an
  empty string. [observed: probe] [source: changelog] `## 2.1.119` "Fixed
  plugin MCP servers failing when `${user_config.*}` references an optional
  field left blank".

## Not covered

- `${HOME}` and `${CLAUDE_PLUGIN_DATA}` on Windows and macOS: only Linux was
  observed. The documentation covers `${CLAUDE_PLUGIN_DATA}` on every
  platform; `${HOME}` on Windows is the open one.
- Whether the `/plugin` configuration dialog pre-fills and saves a default,
  which would freeze the default's text at enable time instead of reading the
  manifest's current default on each start. The probe saved options by
  writing `settings.json`, not through the dialog.
- Plugin servers started inside Claude Desktop's Cowork sessions.
