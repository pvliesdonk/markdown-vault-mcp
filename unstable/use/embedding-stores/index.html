    Choosing an embedding store¶

    With an embedding provider configured, the server keeps one vector per section of every note so it can search by meaning. MARKDOWN_VAULT_MCP_EMBEDDING_STORE names the store that keeps them, and MARKDOWN_VAULT_MCP_EMBEDDING_SEARCH how a search reads them. This page is for the operator deciding between them: which store suits a vault, and what each one was measured to cost at two vault sizes.

    Which store suits your vault¶

    Store Set Suits
    sqlite, streamed nothing: the default most vaults. Search memory stays flat as the vault grows, and an edit writes only the changed note, never the whole store.
    sqlite, resident MARKDOWN_VAULT_MCP_EMBEDDING_SEARCH=resident a vault whose server has memory to spare and wants faster searches, keeping per-note writes.
    numpy MARKDOWN_VAULT_MCP_EMBEDDING_STORE=numpy a small vault that is rarely edited. It is the fastest to search, but it holds every vector in memory and rewrites all of them at each save.
    postgres MARKDOWN_VAULT_MCP_EMBEDDING_STORE=postgres and its settings a team that already runs PostgreSQL with pgvector, or wants the vectors off the server's disk, at the cost of a separate service of about half a gigabyte. PostgreSQL embedding store covers running it.

    Streamed and resident search give the same results, apart from the order of notes with equal scores. Without MARKDOWN_VAULT_MCP_INDEX_PATH or MARKDOWN_VAULT_MCP_EMBEDDINGS_PATH, sqlite and numpy keep the vectors in memory, searched resident, and every note is embedded again at each start, which a paid provider bills each time. The Claude Desktop bundle and the Claude Code plugin set no index path yet (#1728).

    Where the vectors live¶

    At MARKDOWN_VAULT_MCP_EMBEDDINGS_PATH when set, otherwise beside MARKDOWN_VAULT_MCP_INDEX_PATH, as index-db-embeddings beside index.db:

    • sqlite keeps one database, index-db-embeddings.sqlite3, and writes each change on its own, durable once written. It does not shrink: space freed by deleted notes or a model change is reused by later writes.
    • numpy keeps index-db-embeddings.v2.json and the index-db-embeddings.v2.m<N>.npy matrix it names, and rewrites both at each save.
    • postgres keeps them in the schema MARKDOWN_VAULT_MCP_EMBEDDING_POSTGRES_SCHEMA names.

    A streamed search reads the vectors from the database in batches of MARKDOWN_VAULT_MCP_EMBEDDING_SEARCH_WORKSPACE_MB (1 MiB by default) instead of holding them all. The workspace bounds one batch of a search, not the server's memory. postgres is always streamed and scores in the database; numpy is always resident. numpy with MARKDOWN_VAULT_MCP_EMBEDDING_SEARCH=streamed, or postgres with resident, refuses to start. The embeddings_status tool reports the mode the store runs in, its workspace, the size of its files (stored_bytes) and the bytes of vectors it holds in memory (resident_vector_bytes). That last figure leaves out the server's other memory, such as the note text a resident store also keeps.

    What each store costs¶

    The figures below come from running the whole server on one host at two vault sizes, twice each (#1899); numpy's peak memory at the larger size is from a later run, after #1936 stopped it copying its vectors when it opens, and postgres's restart is from a later measurement too, after #1937 stopped it reading every note's vectors at each start. Where the two runs differed at the precision shown, both are given as a range. The vectors had 1,024 dimensions; memory is in decimal MB.

    How to read it:

    • Memory. A streamed store's search memory barely moves with the vault. numpy keeps every vector in memory, beside each section's text and metadata, so its memory grows with sections × dimensions. At the larger size that came to about 1.25 GB above the server's own memory, 0.93 GB of it vectors. The PostgreSQL service itself used about 530 MB at rest at the smaller size and 580 MB at the larger, on top of the server.
    • Speed. Resident search stays fast at both sizes. A streamed search reads every vector, so its time grows with the vault: about 0.15 s at the smaller size, about a second at the larger. postgres streams too, but scores in the database. In these runs the sqlite store stayed in the kernel's page cache; a server without spare memory for it reads disk on every search and is slower.
    • Edits. sqlite's figure counts the edited note's pages and the keyword index together; postgres writes its WAL in the database and the keyword index locally; numpy rewrites the whole store on every save.
    • Restarts. No store embeds an unchanged note again after a restart or a crash. At each start the server checks every note against the store; postgres reads what it holds for 500 notes at a time, so it comes back in a time comparable to a local store's. Its figures come from restarts measured on their own, not in a whole run, so they are not directly comparable with the other columns. A database across a network adds a round trip to each of those reads.
    • The first build. Building the index and every vector from nothing peaked at 360 to 470 MB at the smaller size and 2.4 to 3.6 GB at the larger, on every store, which is more than any store needs once it serves (#1938). Size the server's memory for the first build, plus an in-process provider's own memory (FastEmbed takes 1 to 2 GB), and expect a restart, which reads every note again, to come close to it.

    sqlite, resident was not measured. It holds the vectors in memory as numpy does and writes each edit as streamed sqlite does, so its memory and search time are probably close to numpy's, with sqlite's writes.

    What these figures do not cover¶

    The figures are a measured envelope, not a guarantee:

    • one host (an 8-core Intel desktop with about 130 GB of memory and a local ext4 disk), two runs, a third for numpy's peak memory at the larger size, written to a memory-backed folder, and two restarts of postgres at each size measured on their own, not in a whole run; a few percent between runs is within what another run could move;
    • a stand-in embedding provider that makes no network calls, so the build figures, time and memory alike, leave out the real provider, which dominates a real build;
    • PostgreSQL in a container on the same host; a database across a network adds a round trip to every search and every restart check;
    • a uniform synthetic vault (six sections a note); real vaults vary note size and folder shape;
    • memory during a restart was not measured, and neither were several clients at once or a vault larger than 227,640 sections; other vector widths, filesystems and PostgreSQL images in the supported range were left out too.

    Changing store later¶

    A switch starts the new store empty, so on its own it embeds every note again. Run markdown-vault-mcp embeddings import first to copy the vectors across. Upgrading, switching and restoring embeddings covers the switch, the upgrade from 5.x, backups and recovery; Index storage and SQLite covers what the sqlite store needs from its disk.
